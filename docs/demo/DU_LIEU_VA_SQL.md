# Dữ liệu và hợp đồng SQL của 8 UC

Tài liệu thiết kế PostgreSQL 16; đặc tả đích còn phần cần triển khai. Tên trường mới dùng snake_case, PK bigint GENERATED BY DEFAULT AS IDENTITY (trừ UUID phiên/giao dịch); FK cùng kiểu với bảng đích. Tiền numeric(15,0), tỷ lệ numeric(5,2), thời điểm timestamptz, trạng thái text + CHECK. Không đưa CCCD/ảnh rõ vào audit/log.

## Bảng hiện hành

| Nhóm | Bảng và quan hệ |
|---|---|
| Tài khoản | TAI_KHOAN → SINH_VIEN bằng MaTaiKhoan unique; vai trò ADMIN/KETOAN/KYTHUAT/BAOVE/SINHVIEN |
| Phòng | TOA_NHA → PHONG ← LOAI_PHONG; PHONG → GIUONG; SINH_VIEN + GIUONG → DANG_KY_PHONG → LUU_TRU |
| Hóa đơn | PHONG → CHI_SO_DIEN_NUOC (unique phòng/kỳ), HOA_DON (unique phòng/kỳ) → CHI_TIET_HOA_DON, THANH_TOAN; DON_GIA_DICH_VU → chi tiết |
| Sửa chữa | PHONG/SINH_VIEN → YEU_CAU_SUA_CHUA → XUAT_VAT_TU ← VAT_TU |
| An ninh | SINH_VIEN → RA_VAO → VI_PHAM; AUDIT_LOG lưu old/new JSONB |

Schema hiện hành có27bảng, gồm HOC_KY/DOT_DANG_KY, CHINH_SACH_GIAM_GIA/SINH_VIEN_CHINH_SACH và HOAT_DONG/DANG_KY_CONG_ICH/SO_DIEM_CONG_ICH/QUY_DOI_DIEM. Chưa có khách thăm/outbox/hồ sơ mã hóa/hợp đồng đầy đủ. Không diễn giải ERD lịch sử là các bảng đã tồn tại.

## Bổ sung dữ liệu khi triển khai

Mọi bảng có created_at, updated_at, version integer >=1 nếu cập nhật; trạng thái terminal không sửa bằng API trực tiếp. FK dùng RESTRICT cho chứng từ tài chính/lịch sử, không cascade xóa bằng chứng. Index FK và các tổ hợp lọc trạng thái/thời gian; chỉ index JSONB khi có truy vấn cụ thể.

## Ranh giới SQL và transaction

Nghiệp vụ của 8 UC được điều phối trong Java service. Service kiểm tra quyền,
điều kiện nghiệp vụ, thứ tự khóa, transaction, audit và idempotency; repository
chỉ thực hiện các câu SQL đọc/ghi bằng JdbcTemplate. Không gọi stored procedure
cho các luồng này và không chuyển quy tắc nghiệp vụ nhiều bước xuống PostgreSQL.

| UC | Service | Repository và dữ liệu chính | Ranh giới transaction |
|---|---|---|---|
| UC-04 | BookingService | BookingRepository; sinh_vien, dot_dang_ky, giuong, dang_ky_phong, svc_profile, svc_file | Khóa sinh viên/giường; tạo đơn, hồ sơ, giữ giường, audit/outbox cùng transaction |
| UC-12 | RegistrationService | BookingRepository; dang_ky_phong, luu_tru, svc_contract, sinh_vien, giuong, phong | Khóa sinh viên → đơn → giường; duyệt/từ chối và cập nhật các bảng liên quan nguyên tử |
| UC-17 | InvoiceService | InvoiceRepository; chỉ số, giá, occupants, chi phí, hóa đơn/chi tiết, snapshot | Mỗi phòng khóa và phát hành riêng; đối chiếu lại snapshot trước khi ghi |
| UC-08 | PaymentService | PaymentRepository; hóa đơn, thanh toán, phiên, phân bổ, callback | Tạo phiên trước khi gọi mạng; callback xác thực rồi khóa phiên/hóa đơn và cập nhật trong transaction |
| UC-22 | RepairService | RepairRepository; phiếu, phân công, vật tư, xuất kho, lịch sử, đề nghị mua | Khóa phiếu/vật tư; chỉ hoàn tất và xuất kho khi đủ toàn bộ vật tư |
| UC-25 | GateService | GateRepository; thẻ, ra_vào, vi_pham, khách, sự kiện barrier | eventId chống lặp; log và trạng thái barrier chờ xử lý được ghi cùng transaction |
| UC-14 | DisciplineService | DisciplineRepository; vi phạm, quyết định revision, minh chứng, khiếu nại | Khóa sinh viên theo thứ tự rồi khóa vi phạm; toàn batch commit hoặc rollback |
| UC-30 | CommunityService | CommunityRepository; hoạt động, đăng ký, sổ điểm, quy đổi, chứng nhận | Khóa sinh viên/hoạt động; cập nhật chỗ và sổ điểm trong cùng transaction |

`ServiceContext` dùng `TransactionTemplate` và `JdbcTemplate` dùng connection
được Spring quản lý. Lỗi SQL làm transaction rollback; lỗi nghiệp vụ được ném từ
service. Chi tiết các phương thức hiện có và phần chưa triển khai nằm trong
[báo cáo rà soát 8 UC](RA_SOAT_NGHIEP_VU_8UC.md).

Schema hiện hành không định nghĩa function/procedure từ nền cũ. Service của 8 UC
điều phối nghiệp vụ và repository thực hiện SQL trực tiếp bằng JdbcTemplate cho các
nghiệp vụ này. DDL hiện hành nằm trong `database/01_schema.sql`; seed demo nằm
trong `database/02_seed.sql`. Thay đổi schema được review và áp dụng bằng SQL thủ
công, không dùng migration tự động.

Các tên snake_case/bigint ở thiết kế bổ sung là đích; schema hiện tại dùng MaHocKy/MaHoatDong varchar. Khi triển khai API/entity cần mapping kiểu ID rõ ràng, không coi đã đồng bộ toàn bộ contract.
